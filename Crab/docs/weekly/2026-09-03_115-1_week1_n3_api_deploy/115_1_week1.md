# 115 學年度第 1 學期 Week 1

**最後更新：** 2026-09-03  
**主題：** 中文 N3 API 打包、A4500 本機雙模型部署與驗證  
**目前階段：** 實驗部署成功，等待正式分支整合與開機自啟

## 一分鐘報告摘要

本週把中文情緒模型 `N3 v1-warmstart stage 2` 從研究 checkpoint 整理成可搬運、
可驗證的 API，並成功部署到 A4500。現在 A4500 可以同時執行英文 Scheme 1、
中文 N3 與 Whisper，不再依賴原本受防火牆阻擋的 3090 跨主機連線。

可以把整套系統想成「同一間辦公室有兩位情緒辨識專員」：英文交給
Scheme 1，中文交給 N3；面試後端像總機，依 session language 分流。
兩個模型使用相容的三分類格式回覆。中文服務暫停時會安全回 N/A，不會把
中文誤送給英文模型，也不會在情緒節點中斷整場面試。

A4500 三服務並發時顯存峰值為 **10,339 / 19,190 MiB**，仍有約
**8.65 GiB** 餘裕；60 秒 soak 的 1,184 次 N3 請求全部成功。A4500 實測
1 分鐘音訊：中文 N3 約 **0.90 秒**、英文 Crab 約 **0.74 秒**；N3 慢約
20%，但兩者都遠快於即時播放速度。

## 目前架構

```text
中文面試 ─┐
          ├─ A4500 面試後端 ─ zh ─→ N3（127.0.0.1:8002）
英文面試 ─┘                 └ en ─→ Scheme 1（既有服務）
                    ↑
                 Whisper ASR
```

- N3 骨幹：`facebook/wav2vec2-xls-r-300m` +
  `FacebookAI/xlm-roberta-large`，兩個 LoRA adapters 加 SER head。
- 英文 Scheme 1：WavLM-Large + RoBERTa-Large full fine-tune。
- 兩邊共用 `Excited / Unconfident / Neutral_3Class` 三分類契約。
- A4500 本機部署是主方案；NetBird／遠端 3090 僅保留作未來備援。

## 本週完成

### 1. N3 API 與部署包

- 讀取 `mode.json`，固定架構、class order 與 model ID：
  `n3-v1-warmstart-nnime-lora-stage2`。
- 驗證 audio/text LoRA、SER head、normalization stats 與 SHA-256；缺檔、
  放錯目錄或 checksum 不符時 fail fast。
- 固定兩個 Hugging Face backbone revision，支援 offline 啟動。
- 完成 single、batch、long、live、ready、health、metrics endpoints。
- 加入 Bearer token、request ID、輸入上限、bounded queue、timeout、
  backpressure、OOM-safe error 與分段 latency。
- 部署包不含訓練語料、真人錄音、個資或 token。

### 2. A4500 部署與中文分流

- 建立獨立 Python 3.10 venv，未修改既有 Crab venv。
- N3 以 HF offline、Bearer 強制模式啟動於 `127.0.0.1:8002`。
- 依 session language 分流：中文走 N3，英文維持 Scheme 1。
- 中文逐字稿送出前簡轉繁並移除 CJK 字間空格；保存的 ASR 原文不變。
- 中文使用獨立 URL、token 與 timeout；batch 最多 16 句。
- transport、408、429、5xx 有限重試；401／400 不重試。
- N3 離線或長音訊不適合 single fallback 時安全回 N/A，面試 graph 繼續。
- Whisper 已實作 `zh`／`en` language hint，等待正式服務重啟套用。

## 一分鐘音訊速度比較

### A4500 實際部署結果（報告主數據）

| 情境 | 中文 N3 | 英文 Crab | 差異 |
|---|---:|---:|---:|
| 60 秒音訊 `classify-long` | **0.90 s** | **0.74 s** | N3 慢約 22% |
| Batch 5 × 12 秒 | **0.49 s** | **0.41 s** | N3 慢約 20% |
| 面試主路徑的 8 句 batch | **0.93 s** | **0.87 s** | N3 慢約 7% |

面試主路徑另有約 0.91 秒 Whisper ASR，兩個情緒模型共用這段 ASR 成本。
因此應報告為：

> 在 A4500 上，N3 處理 1 分鐘音訊約 0.90 秒，英文 Crab 約 0.74 秒。
> N3 約慢 20%，但仍約為 67 倍即時速度，不會成為面試互動瓶頸。

### 3090 隔離對照

為排除單次測量誤差，另在同一張 RTX 3090 上以相同 60 秒合成 WAV、
`classify-long`、12 秒 window／6 秒 stride、localhost real HTTP 進行測量。
每個模型獨立啟動，warm-up 3 次後量測 20 次，concurrency 1。

| 模型 | Client mean | P50 | P95 | Inference P50 | 約幾倍即時 |
|---|---:|---:|---:|---:|---:|
| 中文 N3 | 638.98 ms | **639.57 ms** | 642.26 ms | 629.00 ms | 93.81× |
| 英文 Scheme 1 | 648.02 ms | **648.31 ms** | 650.13 ms | 637.54 ms | 92.55× |

3090 上兩者幾乎同速，N3 僅快約 1.35%；A4500 上則是 N3 慢約 20%。這表示
絕對延遲與小幅差距會受 GPU、runtime、文字 tokenization 及同機服務狀態影響。
正式報告應以實際部署機 A4500 數據為主，不宣稱某個模型在所有硬體都較快。

以上只計情緒 API，不含錄音、網路上傳或完整面試流程。合成音訊只能比較
速度，不能比較準確率。正常面試會先切成 3–12 秒句段並呼叫 batch，不會每次
把完整 1 分鐘送進 long endpoint。

## 遇到的問題與處理

1. **3090 公網 ingress 不通：** A4500 可 ping 3090，但 TCP 22／1022 timeout。
   因此改用 Plan B：3090 主動上傳 bundle、A4500 下載後本機部署。Plan B 已
   驗證成功，跨主機網路不再是上線阻塞。
2. **Bundle prefetch bug：** `.1` 的 `prefetch_backbones.py` 寫入
   `refs/main` 時多一個 newline，導致 huggingface_hub 0.27.0 離線查找失敗。
   A4500 已手動修正；3090 已建立 `.2` 修正版並重新驗證 checksum。
3. **Long transcript 契約：** N3 `classify-long` 對超過 128 tokens 的逐字稿回
   `400 TEXT_TOO_LONG`；英文舊服務會靜默截斷。正式面試走對齊句段 batch，
   不受影響。若要支援整段長逐字稿，未來應由 client 按 window 分段文字，
   不建議無提示地截斷。
4. **完整面試後段錯誤：** 情緒節點完成後，MiniMax-M3 manager 回傳不完整
   tool arguments，造成 turn evaluation failure。這是既有 LLM manager 問題，
   與 N3、Scheme 1 和分流無關，但會影響完整面試收尾。
5. **服務尚未常駐：** N3 目前由 tmux 執行，主機重開後不會自動恢復。
